# 仕様書の細分化ガイド (WordPress プラグイン)

## 目的

本ドキュメントは、**AI 伴走開発** と **後日のメンテナンス** の両方を意識した「仕様書のどこまで細分化するか」のベター・プラクティスを整理し、S2J Alliance Manager プロジェクトへの具体的な改善案を示します。

---

## 1. なぜ細分化するか

### 1.1 AI 伴走開発の観点

- **コンテキストの焦点**: 単一の巨大 SPEC だと、タスクに関係ない章まで読み込まれ、トークン消費が増えたり関連部分の精度が落ちたりする。
- **指示の明確さ**: 「`docs/rest_api_spec.md` のエンドポイント定義に従って実装して」のように、**参照すべきファイルを指定** できると再現性が高い。
- **変更の局所化**: 「Carousel の条件を4〜8から3〜10に変える」といった変更は、`carousel_spec.md` だけを更新対象にできる。

### 1.2 後日メンテナンスの観点

- **影響範囲の把握**: データ構造を変えるときは `data_dictionary.md` と `rest_api_spec.md` の両方を確認する、といった **チェックリスト** が立てやすい。
- **オンボーディング**: 新規参加者や将来の自分が「何がどこに書いてあるか」を把握しやすい。
- **レビュー・PR**: 「この PR は REST API 仕様の変更のみ」のように、**変更単位** で説明しやすい。

### 1.3 WordPress プラグイン特有の考慮

- **PHP / JS の境界**: データの真実の源 (CPT、メタキー、option) は PHP、型・UI は TypeScript と分かれるため、「データ定義」を 1 か所にまとめると両言語で参照しやすい。
- **ブロックと REST API**: Gutenberg ブロックの属性・表示と、REST API のリクエスト/レスポンスは変更頻度が高く、独立した spec にすると変更時の衝突が減る。
- **共通仕様との関係**: 既存の [WP_PLUGIN_SPEC](https://github.com/stein2nd/wp-plugin-spec) は「起点」として参照し、プラグイン固有の部分だけを細分化する形が扱いやすい。

## 2. 細分化のベター・プラクティス (一般論)

### 2.1 分離するとよい「単位」

| 単位 | 理由 |
|------|------|
| **プロジェクトの存在理由・概要** | オンボーディング、AI のタスク理解で常に参照する。短い 1 ファイルが望ましい。 |
| **データの定義 (モデル、型、メタキー、option)** | バリデーション、API、フロントの「真実の源」。1 か所にまとめると不整合が減る。 |
| **REST API (エンドポイント、リクエスト/レスポンス、権限)** | フロントとバックの契約。変更時に影響範囲が明確になる。 |
| **複雑なドメインロジック (数式、条件、バリデーション)** | 例: スコア算出、Carousel の有効条件。仕様変更時にそのファイルだけ更新すればよい。 |
| **コード構造、責務 (どのファイルが何をするか)** | 新規機能追加時やリファクタ時に参照する。 |
| **外部連携・取込ルール** | 例: 郵便データ取込。他 spec と独立して更新できる。 |

### 2.2 分離のしすぎを避ける

- **1章が数段落程度** の内容を無理にファイル分割しない。**変更がまとめて起こる単位** で切る。
- **参照関係** を増やしすぎない。`specs.md` から各 spec へのリンクを1階層でまとめておく。
- **実装状況、Backlog、品質レポート** は、プロジェクト全体の「今の状態」なので、**1ファイル (例: `SPEC.md` のまま、または `status.md`)** にまとめておいてもよい。

### 2.3 起点ファイル (specs.md) の役割

- プロジェクトの仕様書の **目次** と **参照先** だけを記載する。
- 共通仕様 (WP_PLUGIN_SPEC 等) へのリンク、各細分化 spec へのリンク、必要なら 1 段落の概要。
- これにより「仕様は `docs/specs.md` から」と一言で伝えられる。

## 3. S2J Alliance Manager 向けの具体的な改善案

現状は `docs/SPEC.md` に約 1,134 行が集約されています。以下は、lead-validation-assist の分割思想を WordPress プラグイン向けに適用した **推奨構成** です。

### 3.1 推奨ファイル構成

```
docs/
├── specs.md                    # 仕様書の起点 (目次、リンクのみ)
├── overview.md                 # プロジェクトの存在理由、概要、基本情報
├── architecture.md             # フォルダ構成、主要ファイル、責務
├── data_dictionary.md          # データ構造、型定義、CPT、メタキー、option
├── rest_api_spec.md            # REST API エンドポイント、リクエスト/レスポンス、権限
├── block_spec.md               # Gutenberg ブロック (属性、表示、編集) ＋ Classic 対応方針
├── admin_ui_spec.md            # 管理画面の機能、UI/UX (レイアウト、フォーム、一覧、モーダル等)
├── carousel_spec.md            # Carousel の条件、カウント、表示、バリデーション (付録から独立)
├── ffmpeg_spec.md              # FFmpeg 統合、ポスター生成、動画まわり (任意)
├── style_and_components.md     # スタイル設計、コンポーネント設計、国際化 (任意で 1 本に)
└── status.md                   # 実装状況サマリー、Backlog、品質レポート、まとめ (任意)
```

**必須としたいのは上から 5 つ** (`specs.md` / `overview.md` / `architecture.md` / `data_dictionary.md` / `rest_api_spec.md`) です。  
`block_spec` 以降は、変更頻度と「まとめて読みたいか」で統合・分割を調整するとよいです。

### 3.2 各ファイルの役割と SPEC.md との対応

| 新ファイル | 役割 | 現在の SPEC.md の主な対応箇所 |
|------------|------|-------------------------------|
| **specs.md** | 起点。共通仕様へのリンク、各 spec へのリンク、1段落の概要。 | はじめに |
| **overview.md** | 存在理由、目的、特徴、基本情報 (名称、スラッグ、ライセンス等)。 | §1 プラグイン概要 |
| **architecture.md** | フォルダ構成、主要ファイル、技術スタック、ビルド、責務。 | §2 プロジェクト構成、§3 技術スタック、開発環境 |
| **data_dictionary.md** | ContentModel / RankLabel の型、設定配列、CPT、メタキー、option、データフロー。 | §9.1、§9.2 |
| **rest_api_spec.md** | エンドポイント一覧、メソッド、URL、リクエスト/レスポンス、権限、セキュリティ。 | §9.3、§9.3.2 |
| **block_spec.md** | ブロック属性、フロント表示、Carousel の「表示側」の前提、Classic 対応方針。 | §7 |
| **admin_ui_spec.md** | 管理画面レイアウト、各機能 (ランクラベル、コンテンツ一覧、設定フォーム、モーダル、FFmpeg 等)。 | §5.2、§8 |
| **carousel_spec.md** | 子要素数カウント、有効条件 (4〜8)、フロント表示、バリデーション。 | 付録 A.1–A.4 |
| **ffmpeg_spec.md** | FFmpeg パス、テスト、ポスター生成、動画/ポスターの扱い (必要なら)。 | §5.3、§8.1.6–8.1.8 |
| **style_and_components.md** | スタイル原則、コンポーネント一覧、国際化方針。 | §4、§5.1 |
| **status.md** | 実装状況、Backlog、品質、まとめ。 | §10–§13 |

### 3.3 改善の優先度 (S2J の場合)

1. **高**: `specs.md` の作成、`overview.md` / `data_dictionary.md` / `rest_api_spec.md` の分割
   → AI が「データと API の契約」を正確に参照できるようにする。
2. **高**: `carousel_spec.md` の独立
   → 条件・バリデーション・表示が1ファイルにまとまり、変更時の影響が追いやすい。
3. **中**: `architecture.md`、`block_spec.md` の分割
   → ブロックやビルド周りの変更時に参照する spec が明確になる。
4. **中〜低**: `admin_ui_spec.md` の分割 (必要なら `rank_label_ui_spec.md` などにさらに分割)
   → 管理 UI の記述が長いため、担当領域ごとに分けるとレビューしやすい。
5. **低**: `status.md` への分離、`ffmpeg_spec.md` / `style_and_components.md` の独立
   → 必要に応じて。まずは `SPEC.md` の「実装状況・Backlog・まとめ」をそのまま1ファイルにまとめてもよい。

### 3.4 移行時の注意

- **SPEC.md は残すか、`status.md` に縮約するか** を決める。  
  - 残す場合: 「詳細は `docs/specs.md` から各 spec を参照」と先頭に注記し、徐々に本文を各ファイルに移す。
  - 縮約する場合: 実装状況・Backlog・品質・まとめだけを `status.md` に移し、`SPEC.md` は `specs.md` へのリダイレクト的説明にしてもよい。
- 各 spec の **先頭に「このドキュメントの役割」と、必要なら `data_dictionary.md` / `rest_api_spec.md` などへの相互リンク** を 1 行ずつ書いておくと、AI と人の両方がたどりやすい。

## 4. まとめ

- **WordPress プラグインでも**、lead-validation-assist と同様に「存在理由・データ・API・複雑なロジック・コード構造」は **ファイル単位で分けておく** と、AI 伴走とメンテナンスの両方に有利。
- **細かく切りすぎない** こと。「変更がまとめて起こる単位」で切り、起点 (`specs.md`) から1階層でリンクする構成が扱いやすい。
- **S2J Alliance Manager** では、まず **specs.md / overview / data_dictionary / rest_api_spec / carousel_spec** の5本を用意し、その後 **architecture / block_spec / admin_ui_spec** を分け、必要に応じて status / ffmpeg / style を分離する **段階的移行** を推奨する。

この方針に沿って、必要なら `docs/specs.md` と `docs/overview.md` のひな形から作成していくことができます。
